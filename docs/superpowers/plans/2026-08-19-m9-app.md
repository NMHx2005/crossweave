**Goal:** Turn `cw` into a full-screen interactive app (like `claude`, `codex`, `opencode`) — running bare `cw` opens the interface directly, with workspace switcher, sessions as real terminal panes inside the app, mouse + keyboard control, and inter-session messaging — while keeping every existing subcommand for scripting.

**Architecture:** The daemon already has everything the app needs: `session.attach` replays scrollback and streams `session.data` (with `sessionId`) to any number of subscribers per session (`runtime.subscribe` uses `Set<MethodContext>`), `session.input`/`session.resize` drive agents, `tui.event`/`tui.invalidate` push radar/convergence state, and the message bus holds inter-session traffic. This plan builds a new `src/app/` module (state reducer, line buffer with ANSI-subset parsing, layout/hit-testing, renderables, orchestrator) and rewires `src/cli/commands/tui.ts` to delegate to it; existing pure helpers (`formatSessionRow`, `formatFeedLine`, `landAllInOrder`, …) move to `src/app/format.ts` and are re-exported so current tests keep passing. Only one daemon addition is needed: a read path for the human to see bus messages (`message.list` RPC + refetch signal on send).

**Tech Stack:** @opentui/core 0.5.3 (already a dependency; `BoxRenderable`/`TextRenderable`/`InputRenderable`/`SelectRenderable`/`CliRenderer`/`CliRenderEvents` + `lib/parse.mouse`'s `RawMouseEvent`), @opentui/keymap, existing JSON-RPC daemon client, bun:test.

## Global Constraints

- Bare `cw` (no subcommand, no `-h`/`-v`) launches the app; every existing subcommand keeps working unchanged; `cw tui` stays as an alias.
- In-app session interaction is purely RPC-driven (`session.attach`/`session.input`/`session.resize`/`session.data`); no PTY relay code, no suspend/resume, no child `cw session attach` process from the app.
- One daemon connection can attach to many sessions (`runtime.subscribe` is keyed by session with `Set<MethodContext>`, verified) — the app uses a single connection.
- V1 ANSI handling is a **subset** — see Task 0 Step 2b for the specific risk this scopes around, and the decision gate it requires before Task 4 is written for real. Baseline behavior: `\r\n`/`\r`/`\n` line control is normalized, everything else (SGR color/bold, cursor moves, alternate screen, OSC) is stripped to plain text — a rolling log per session, like `--print` output. Full VT emulation (a real terminal emulator per pane) is explicitly out of scope for v1; if Task 0 Step 2b shows plain-text stripping makes wrapped agents' own interactive UI (spinners, in-place menus) unreadable, the fallback is documenting that limitation loudly (Task 9) and leaning on `cw session attach` (kept, unchanged) for full-fidelity interaction — not silently shipping a broken-looking pane.
- Mouse v1: click-to-focus session pane, click sidebar item to select, wheel scroll of focused pane/feed, clickable action buttons in the status bar.
- Pure logic (state, buffer, layout, key/mouse mapping) lives in functions without renderer/RPC deps and carries the tests; renderer wiring stays thin (existing pattern: `tests/cli/tui.test.ts` fakes the renderer).
- No new runtime dependencies. No polling: all refreshes come from `tui.event`/`tui.invalidate` notifications.
- Errors use `CrossweaveError`; user-facing copy in English; comments in English.

- [ ] **Step 2b: The real risk — redraw-in-place, not color (decision gate for Task 4)**

Color is the easy 20% of "ANSI handling"; the actual risk to the app *feeling* polished is that `claude`/`cursor-agent` are themselves full-screen interactive CLIs — they use cursor-repositioning and in-place redraw for spinners, streaming output, and (critically) permission-approval menus, not just `print`-and-scroll. Stripping "cursor moves, alternate screen" (as the Global Constraints baseline does) does not make that content disappear — it makes every redraw frame land as a *new* appended line, because the escape sequence that would have repositioned the cursor back to overwrite the previous frame is silently discarded. The pane fills with dozens of near-duplicate lines instead of one clean line that updates in place. This is exactly the failure mode M8 avoided by using a real PTY passthrough (`cw session attach`) instead of parsing/re-rendering — full terminal emulation of an arbitrary nested CLI is genuinely hard (it's what xterm.js/ttyd exist to solve), which is also why the Global Constraints explicitly scope full VT emulation out.

Probe with a real, running `claude` session (not the fake agents used elsewhere in this plan): attach via the existing `cw session attach` path, trigger a permission-approval prompt or a streaming response, and capture the raw `session.data` chunks (log them to a file). Run those captured chunks through the Step 2 verdict's rendering path (plain `stripAnsiSubset` if `TextBuffer` doesn't parse ANSI, or `TextBufferRenderable` directly if it does) and look at the result with real eyes, not just unit-test assertions. Record one of two verdicts in Task 4/6's target files:

- **Acceptable-for-v1**: redraw frames are visually distinguishable/tolerable as a scrolling log (e.g. Claude Code's own output is already mostly line-oriented outside of spinners) → proceed with the plain-text `LineBuffer` approach as scoped.
- **Not acceptable**: menus/spinners spam the pane unreadably → do not silently ship it. Either (a) narrow v1's pane to a *preview only* (last N lines, explicitly labeled non-interactive, with a keybinding that shells out to the existing `cw session attach` for real interaction — reusing M8's suspend/resume attach-in-place code, which already exists and already handles full VT correctly), or (b) bring this back to design before writing Task 4, since it changes the shape of `LineBuffer`/`render.ts` significantly. Do not let Task 4's code (already fully written below) ship unconditionally without this check — it was drafted before this risk was identified.

**VERDICT: Not acceptable, run and measured (not hypothetical) — 2026-08-19.**
Probed a real `claude` T2 session in this repo (`session new probe-redraw --agent claude`,
raw `session.data` captured via a throwaway `DaemonClient` script, no PTY/terminal
rendering involved — the exact bytes `LineBuffer` would receive). Sent one prompt
("List the files... then say done") and captured ~20s of the "thinking" phase:
**195 chunks total, 159 of them (81.5%)** were pure status-line redraws of this shape:

```
\x1b[?25l\x1b[H\r\x1b[16B\x1b[38;5;174m✻\x1b[27G\x1b[38;5;246m74\x1b[39m\x1b[24;1H\x1b[20;3H\x1b[?25h
```

— hide cursor, jump to an absolute row/col, print a spinner glyph + running token
count, jump elsewhere, show cursor. Run through the plan's own `stripAnsiSubset`
exactly as specified (Step 3's implementation, unmodified), this single frame
becomes `"\n✳74"` — **a new scrollback line**, because the frame's only `\r` is
vestigial (the actual repositioning is `\x1b[H`/`\x1b[16B`/`\x1b[24;1H`, all CSI
cursor-addressing, which stripping removes) and stripAnsiSubset unconditionally
maps every lone `\r` to `\n`. There is no cheap fix via smarter `\r` handling —
these frames barely use `\r`; the redraw mechanism is absolute cursor addressing,
which is full VT territory by definition. At this rate a real multi-minute "thinking"
turn would dump low hundreds to low thousands of near-duplicate one-glyph lines
into the pane, burying any real content in the "last `h-1` lines" view Task 6
plans to render.

**Chosen mitigation for v1 (option (c), narrower than the two Step 2b sketched):**
rather than either full preview-only demotion (a) or reopening design (b),
special-case this one common, high-volume pattern: a chunk that (i) contains
`\x1b[?25l` and `\x1b[?25h` (cursor hide/show bracketing — Claude Code's own
status-line convention) and (ii) contains no `\n` after stripping is a **status
update, not scrollback content** — route it to a small ephemeral one-line status
slot per pane (e.g. `⋯ thinking (74 tokens)`) instead of `LineBuffer.append`,
overwriting in place each tick. Everything else (real streamed text, tool output,
actual multi-line content) still goes through `LineBuffer` unchanged. This does
not attempt full VT emulation and will still fail to render rarer full-screen
constructs (e.g. an interactive permission-approval menu, not exercised by this
probe's simple prompt) — those remain a `cw session attach` job, and Task 9's
smoke checklist must call that out explicitly. Task 4 below needs a
`isStatusFrame(chunk: string): boolean` predicate and `LineBuffer` needs a
non-scrollback status slot before this task is considered done. **Confirmed
2026-08-19 — proceed with option (c).**

```typescript
import type { SessionRow } from '../db/repositories/session.js';

export const FEED_MAX_LINES = 200;

export interface AppState {
  workspaceId: string | null;
  workspaces: { id: string; name: string }[];
  sessions: SessionRow[];
  selectedSessionId: string | null;
  focusedSessionId: string | null;
  // false = nav mode: bare letters are global shortcuts (j/k/n/l/x/g/q).
  // true = typing mode: every key routes to the focused session's session.input
  // until Escape. See Task 6 — without this, a focused pane could never
  // receive j/k/n/l/g/x/q as literal text.
  inputMode: boolean;
  feed: string[];
  messages: MessageView[];
  notifyCount: number;
}

export interface MessageView {
  id: string; from: string; to: string; type: string; trust: string; body: string; createdAt: string;
}

export const initialState: AppState = {
  workspaceId: null, workspaces: [], sessions: [],
  selectedSessionId: null, focusedSessionId: null, inputMode: false,
  feed: [], messages: [], notifyCount: 0,
};

export type AppAction =
  | { type: 'workspacesLoaded'; workspaces: { id: string; name: string }[] }
  | { type: 'workspaceSwitched'; workspaceId: string }
  | { type: 'sessionsLoaded'; sessions: SessionRow[] }
  | { type: 'sessionSelected'; sessionId: string }
  | { type: 'focusPane'; sessionId: string | null }
  | { type: 'inputModeChanged'; value: boolean }
  | { type: 'feedAppended'; line: string }
  | { type: 'messagesLoaded'; messages: MessageView[] }
  | { type: 'notifyCountIncremented' };

export function reducer(state: AppState, action: AppAction): AppState {
  switch (action.type) {
    case 'workspacesLoaded': {
      const next = { ...state, workspaces: action.workspaces };
      if (next.workspaceId === null && action.workspaces.length > 0) next.workspaceId = action.workspaces[0]!.id;
      return next;
    }
    case 'workspaceSwitched':
      return { ...state, workspaceId: action.workspaceId, selectedSessionId: null, focusedSessionId: null, inputMode: false };
    case 'sessionsLoaded': {
      const ids = new Set(action.sessions.map((s) => s.id));
      const selected = state.selectedSessionId !== null && ids.has(state.selectedSessionId) ? state.selectedSessionId : action.sessions[0]?.id ?? null;
      const focused = state.focusedSessionId !== null && ids.has(state.focusedSessionId) ? state.focusedSessionId : selected;
      return { ...state, sessions: action.sessions, selectedSessionId: selected, focusedSessionId: focused };
    }
    case 'sessionSelected':
      return { ...state, selectedSessionId: action.sessionId };
    case 'focusPane':
      // Changing focus always drops out of typing mode — the previously-focused
      // pane's keystrokes must never leak to whatever gets focus next.
      return { ...state, focusedSessionId: action.sessionId, inputMode: false };
    case 'inputModeChanged':
      return { ...state, inputMode: action.value };
    case 'feedAppended': {
      const feed = [...state.feed, action.line];
      if (feed.length > FEED_MAX_LINES) feed.splice(0, feed.length - FEED_MAX_LINES);
      return { ...state, feed };
    }
    case 'messagesLoaded':
      return { ...state, messages: action.messages };
    case 'notifyCountIncremented':
      return { ...state, notifyCount: state.notifyCount + 1 };
  }
}
```

```typescript
export function stripAnsiSubset(input: string): string {
  // CSI: ESC [ params? final(byte 0x40-0x7E). OSC: ESC ] ... BEL or ESC \.
  let out = '';
  let i = 0;
  while (i < input.length) {
    const c = input[i]!;
    if (c === '\x1b') {
      if (input[i + 1] === '[') {
        i += 2;
        while (i < input.length && !(input[i]! >= '\x40' && input[i]! <= '\x7e')) i++;
        i++; // skip the final byte
      } else if (input[i + 1] === ']') {
        i += 2;
        while (i < input.length && input[i] !== '\x07' && !(input[i] === '\x1b' && input[i + 1] === '\\')) i++;
        i += input[i] === '\x07' ? 1 : 2;
      } else {
        i++;
      }
    } else {
      out += c;
      i++;
    }
  }
  return out.replace(/\r\n/g, '\n').replace(/\r/g, '\n');
}

// Task 0 Step 2b's mitigation: the real `claude` probe (2026-08-19) found 159/195
// chunks over ~20s of "thinking" were pure cursor-hide/redraw/cursor-show status-line
// updates — stripping them as ordinary content would flood `lines` with one
// near-duplicate line per animation tick. Recognized by the cursor-visibility
// bracket alone (not by content), so it works for the token-count spinner tested
// here as well as similar single-line status redraws the same convention covers.
export function isStatusFrame(chunk: string): boolean {
  if (!chunk.includes('\x1b[?25l') || !chunk.includes('\x1b[?25h')) return false;
  return !stripAnsiSubset(chunk).includes('\n');
}

export class LineBuffer {
  private readonly buf: string[] = [];
  private _statusLine: string | null = null;
  constructor(private readonly maxLines: number) {}

  get lines(): readonly string[] {
    return this.buf;
  }

  get statusLine(): string | null {
    return this._statusLine;
  }

  append(chunk: string): void {
    if (isStatusFrame(chunk)) {
      this._statusLine = stripAnsiSubset(chunk);
      return;
    }
    const clean = stripAnsiSubset(chunk);
    if (clean === '') return;
    const parts = clean.split('\n');
    const last = this.buf.pop() ?? '';
    const merged = last + parts.shift()!;
    if (merged !== '') this.buf.push(merged);
    for (const p of parts) {
      if (p !== '') this.buf.push(p);
    }
    this.trim(this.maxLines);
  }

  trim(maxLines: number): void {
    if (this.buf.length > maxLines) this.buf.splice(0, this.buf.length - maxLines);
  }

  clear(): void {
    this.buf.length = 0;
    this._statusLine = null;
  }
}
```

```typescript
export interface Rect { x: number; y: number; w: number; h: number }
export interface AppLayout { sidebar: Rect; panes: Rect[]; feed: Rect; status: Rect }

const SIDEBAR_W = 24;
const STATUS_H = 1;
const FEED_H = 10;

export function computeLayout(cols: number, rows: number, paneCount: number): AppLayout {
  const status: Rect = { x: 0, y: Math.max(rows - 1, 0), w: cols, h: 1 };
  const feed: Rect = { x: 0, y: Math.max(status.y - FEED_H, 0), w: cols, h: Math.max(rows - 1 - FEED_H, 0) };
  const sidebar: Rect = { x: 0, y: 0, w: Math.min(SIDEBAR_W, cols), h: Math.max(feed.y, 0) };
  const mid: Rect = { x: sidebar.w, y: 0, w: Math.max(cols - sidebar.w, 0), h: Math.max(feed.y, 0) };
  const n = Math.max(paneCount, 1);
  const pw = Math.floor(mid.w / n);
  const panes: Rect[] = [];
  for (let i = 0; i < n; i++) {
    const x = mid.x + i * pw;
    const w = i === n - 1 ? mid.w - i * pw : pw;
    panes.push({ x, y: mid.y, w: Math.max(w, 0), h: mid.h });
  }
  return { sidebar, panes, feed, status };
}

export function hitTest(layout: AppLayout, x: number, y: number): { zone: 'sidebar' | 'feed' | 'status' | 'pane'; index: number } {
  if (y >= layout.status.y && y < layout.status.y + layout.status.h) return { zone: 'status', index: 0 };
  if (y >= layout.feed.y && y < layout.feed.y + layout.feed.h) return { zone: 'feed', index: 0 };
  if (x < layout.sidebar.w) return { zone: 'sidebar', index: 0 };
  for (let i = 0; i < layout.panes.length; i++) {
    const p = layout.panes[i]!;
    if (x >= p.x && x < p.x + p.w && y >= p.y && y < p.y + p.h) return { zone: 'pane', index: i };
  }
  return { zone: 'sidebar', index: 0 };
}
```

```typescript
import type { AppState } from './state.js';

export type IntentAction =
  | { type: 'newSession' } | { type: 'land' } | { type: 'landAll' }
  | { type: 'kill' } | { type: 'gc' } | { type: 'quit' }
  | { type: 'focusNext' } | { type: 'focusPrev' }
  | { type: 'enterInputMode' } | { type: 'exitInputMode' };

const NAV: Record<string, IntentAction> = {
  j: { type: 'focusNext' }, k: { type: 'focusPrev' },
  n: { type: 'newSession' }, l: { type: 'land' }, 'shift+l': { type: 'landAll' },
  x: { type: 'kill' }, g: { type: 'gc' }, q: { type: 'quit' },
};

// key names below ('return', 'escape') are placeholders pending Step 4's
// required runtime check against @opentui/keymap's actual KeyEvent.name
// values — confirm before wiring into app.ts (see this task's Interfaces note).
export function keyToAction(key: string, state: AppState): IntentAction | 'input' | null {
  // Typing mode: everything is literal input except the one way out. Checked
  // FIRST and unconditionally — nav-mode shortcuts must never intercept a
  // keystroke meant for the agent, or the user could not type ordinary text
  // containing j/k/n/l/g/x/q into a focused session.
  if (state.inputMode) {
    return key === 'escape' ? { type: 'exitInputMode' } : 'input';
  }
  if (key === 'return' && state.focusedSessionId !== null) return { type: 'enterInputMode' };
  const nav = NAV[key];
  if (nav !== undefined) return nav;
  // No `focusedSessionId && key.length === 1` fallback here — that was the bug
  // this task fixes. In nav mode, an unmapped key is simply ignored; the only
  // way into 'input' routing is inputMode, entered via Enter (above) or a
  // mouse click on a pane (app.ts Step 5 sets inputMode alongside focus).
  return null;
}
```
